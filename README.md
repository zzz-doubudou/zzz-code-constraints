# zzz-code-constraints

一个用于 Codex 的代码约束 Skill。

它以 `karpathy-guidelines` 为通用编码基线，并补充一组偏向简单、明确、可审查和低风险修改的个人规则。

## 适用场景

当任务涉及以下内容时使用本 Skill：

- 代码设计和计划制定
- 源代码修改、重构和代码审查
- 测试和本地验证
- 数据库脚本生成或修改
- 业务服务、API、SDK 或命令行工具的交互

本 Skill 是约束层，不会自动选择其他工作流或技术 Skill。

## 核心规则

### 1. 修改前确认执行方式

只要任务涉及代码或数据库脚本修改，且用户没有明确说明以下内容：

- 修改哪些类、文件或成员
- 每个类、文件或成员具体改什么

就必须先询问用户选择执行方式：

1. **先输出计划**：输出具体修改计划，等待用户确认后再修改。
2. **直接改代码**：检查相关代码后直接实施，不等待单独的计划确认。

用户已经明确选择执行方式，或已经给出完整修改计划时，不重复询问。

在用户作出选择前，可以进行必要的定向只读检查，但不能编辑代码。

### 2. 计划必须具体

实施前的计划需要说明：

- 受影响的类、接口、记录或模块
- 将修改的方法、属性、字段或其他成员
- 行为或职责的变化
- 相关测试和验证命令

不列出没有证据支持的推测文件或类型。

### 3. 保持修改简单

- 只实现请求的行为，不添加臆测功能。
- 不为一次性需求创建抽象、包装层、配置点或扩展点。
- 不拆分只是在隐藏几行代码的方法。
- 只有在存在复用、独立契约、生命周期、明显复杂度或清晰度收益时才保留方法边界。
- 保留现有公共契约，除非需求明确要求改变。
- 只删除本次修改造成的无用代码。

### 4. 控制搜索和修改范围

- 从精确搜索相关功能、类型、方法、错误或数据库对象开始。
- 只读取理解当前修改所需的最小上下文。
- 只有在依赖关系、契约、测试、构建错误或运行时依赖证明必要时才扩大范围。
- 不顺手重构无关代码，不修改无关配置。
- 发现无关问题时单独报告，不扩大当前实现范围。

### 5. 服务层调用链不得擅自重构

服务层调用链的计数规则如下：入口服务方法算第 1 层，每次连续的服务到服务调用增加 1 层。到达第 4 个服务方法时，视为调用链超过 3 层。

如果相关调用链超过 3 层，必须向用户反馈：

- 具体调用路径
- 当前调用深度
- 受影响的行为
- 实际风险
- 可选处理方式和取舍
- 推荐方案及推荐理由

在用户决定前，不得擅自合并、拆分、内联、移动职责或以其他方式重构这条调用链。安全的无关工作可以继续；如果当前需求必须先改变调用链才能完成，则暂停该部分并等待用户决定。

可选处理方式通常包括：

- 保持现状：适用于职责清晰、调用深度有合理原因且测试或可观测性足够的场景。
- 合并或内联透传方法：适用于方法没有独立规则、契约、复用价值或生命周期的场景。
- 归拢业务职责：将完整的业务规则移动到真正拥有该职责的服务或领域组件。
- 使用已有编排入口：当多个服务共同协调一个用例时，优先使用已有的应用层编排器或工作流入口。

### 6. 优先使用代码驱动的业务交互

在存在稳定代码入口时，优先使用业务服务、领域 API、SDK、应用 API、命令行接口或脚本。

不要通过直接改数据库或一次性 UI 操作绕过已有业务规则。只有在没有合适 API、确实需要人工判断或用户明确要求时，才使用手工 UI 操作，并说明原因。

### 7. 测试代码保持本地

测试代码默认只用于本地验证，不提交到 Git，除非用户明确要求提交。

对于 C#：

- 测试逻辑可以放到独立的 partial class 文件中。
- 仅为本地测试创建的生产代码、服务、注册和入口必须放在 `#if DEBUG` 与 `#endif` 之间。
- 业务代码不得依赖测试专用服务。

### 8. 注释要解释意图

本次创建或实质修改的类型、类、接口、记录、构造函数、方法、属性、字段、事件及其他声明成员，都需要按照项目约定补充有价值的注释。

注释应说明意图、约束、业务规则、状态变化、算法或兼容性处理，不要只重复代码名称或下一行代码。

### 9. 数据库脚本限制

- 允许按数据模型需要添加主键。
- 不添加普通索引、唯一索引、聚簇索引或其他非主键索引。
- 不添加外键约束或外键索引。
- 为创建或实质修改的数据库对象添加数据库原生元数据注释，至少覆盖数据库或 Schema、表和列；视图、过程、函数、触发器、序列和约束等对象也应覆盖。
- 遵循目标数据库的方言、命名、类型、迁移和事务约定。
- 完成前检查脚本中是否存在禁止的索引或外键语句，并确认对象注释完整。

## 使用方式

将本目录复制到 Codex 的 Skill 目录中：

```text
<CODEX_HOME>\skills\zzz-code-constraints\
```

如果没有设置 `CODEX_HOME`，通常使用：

```text
%USERPROFILE%\.codex\skills\zzz-code-constraints\
```

目录至少需要包含：

```text
zzz-code-constraints/
|-- SKILL.md
`-- agents/
    `-- openai.yaml
```

在 Codex 中显式使用：

```text
Use $zzz-code-constraints for this coding task.
```

也可以让 Codex 根据 Skill 描述自动选择。

## 执行示例

### 未明确修改范围

用户：

```text
帮我优化这个订单功能。
```

应先询问：

```text
当前还没有明确修改哪些类、文件或成员，以及具体改什么。请选择：

1. 先输出计划，确认后再改
2. 直接改代码
```

### 用户选择先输出计划

应先检查相关代码，然后输出具体的类、文件、成员、行为变化、测试和验证命令；在用户确认前不修改代码。

### 用户选择直接改代码

应先进行必要的定向检查，简要说明计划，然后在同一轮完成代码修改和验证。

### 服务层调用链超过 3 层

例如：

```text
OrderService.Create
  -> PricingService.Calculate
    -> DiscountService.Apply
      -> CouponService.Validate
```

应报告该调用链为 4 层，说明风险并给出处理建议，然后等待用户决定是否重构，不应直接改写调用链。
